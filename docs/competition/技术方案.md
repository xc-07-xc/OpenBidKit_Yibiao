# 易标投标工具箱 · 多 Agent 编排方案（赛道一）

> 定位：**面向强约束文档生产的领域 Agent Harness**。以招投标为参考场景，提供知识层、Agent 层、编排层、调度层、验证层与反馈层的完整闭环；标书是这套 Harness 的第一个负载。

## 1. 为什么选招投标

| 特征 | 对 Agent 编排的意义 |
| --- | --- |
| 输入是几十到几百页的招标文件 | 需要解析、抽取、结构化，而不是一次性问答 |
| 资格、技术、商务、法规多类要求互相约束 | 天然需要多角色分工与共享上下文 |
| 错一个资格项就可能废标 | 必须有验证器与人工闸门，不能只靠"模型自觉" |
| 成稿长、口径多 | 需要一致性检查与定向返工，而不是整篇重写 |
| 企业有历史标书、资质、业绩 | 知识库不是装饰，而是资格判断与正文生成的依据 |

## 2. 总体架构


## 3. 六个考察点的实现

### 3.1 知识库定义与集成

- **入库**：文档 → 语义块（heading_path）→ 程序筛除 → LLM 候选条目 → 补漏回收，落 `knowledge_*` 六张表。
- **读**：`searchKnowledge()` 按阶段关键词检索，拼成「本地知识库参考资料」注入 Prompt，并标注"仅作线索、不足以证明已具备材料"。
- **写**：每阶段产物自动 `importPipelineArtifact()` 回写知识库「流水线产物」文件夹，形成"越跑越厚"的闭环。
- **边界**：当前为关键词检索（SQL `instr`），无向量/重排/引用锚点；这是下一阶段重点。

### 3.2 Agent 团队定义

7 个角色：总控编排、文档解析、资格匹配、技术响应、法规案例、正文生成、质量守门。
每个阶段是独立的 Pi Agent Session（独立工作区与会话记录），并显式声明工具白名单：

| 阶段 | 自定义工具 |
| --- | --- |
| 解析 / 资格 / 技术 / 生成 / 质检 | `json-validation`、`report-failure` |
| 法规 | 上述 + `parallel-web-search`、`parallel-web-fetch` |

自动流水线禁用 `ask-user`，避免阶段停在交互问答。原生工具（read/write/edit/bash/grep/find/ls）由运行时保留，用于读写工作区文件。

### 3.3 工作流编排

- LangGraph `StateGraph`：每个闸门阶段拆 `run` / `gate` 两个节点，解决 `interrupt()` 时产物未落 checkpoint 的问题。
- 并行：qualification 闸门后 technical 与 legal 扇出，汇合到 generate。
- 条件边：consistency 的 high 一致性问题触发回退。
- 人工闸门：`interrupt()` 挂起，`Command(resume=...)` 恢复，reject 清空产物并 `goto` 重跑。
- 运行隔离：每次 start 生成 `run_id` 作为 `thread_id`，同一服务可并存多条流水线。
- 异步执行：`/graph/start` 立即返回，Electron 每 2 秒轮询 `/graph/state` 投影回黑板——避免长阶段把 HTTP 拖到超时。

### 3.4 动态调度（当前最弱项，已留出扩展点）

- 现有效果：阶段级并行、单阶段失败重试 1 次、AI 请求作用域队列（暂停/取消传播）、子代理按父任务分池限流。
- 尚未实现：优先级队列、资源感知、按任务选团队、跨项目调度。
- 扩展点：`pipelineAgentConfig.cjs` 已把阶段顺序/并行组/闸门/依赖数据化，调度器可作为编排器外层独立演进。

### 3.5 自我循环（Self-Loop）

- 主回路：`consistency → generate`，问题清单写入 `feedbackNotes` 回传，上限 2 轮，超限转人工。
- 定点返工：返工同时回传上一轮成稿（`previousDraft`），生成阶段只重写质检问题涉及的章节，其余章节保持原样，避免整篇重写带来的口径漂移。
- 次回路：人工打回 → 清空本阶段产物 → 重跑本阶段。
- 分类治理：`missing_material` 只标记不返工，避免"为了让质检通过而编造材料"。
- 可观测：`_metrics` 记录 `reworkRounds` 与评分轨迹 `history`（每轮触发时的分数与 high 问题数），页面展示「质检分 62 → 88」。

### 3.6 结果验证与反馈优化

- 结构验证：每阶段 Ajv JSON Schema 校验 + 归一化，校验失败可由 Agent 运行时识别并重试。
- 语义验证：一致性 Agent 输出 `score / passed / issues[severity, category, scope, suggestion]`，并要求逐条核对实质性条款与评分办法是否在成稿中有明确响应。
- 人工验证：4 个闸门（解析口径、材料缺口、检索依据、成稿定稿）。
- 交付门禁提示：质检未通过时，导出按钮旁明确提示「N 项 high，导出仅作草稿」，避免把未闭环成稿当终稿提交。
- 指标：阶段通过率、一致性评分、自动返工轮次与评分轨迹。
- 边界：尚无评测集与质量回归，法规引用未做 URL 有效性核验。

## 4. 复现与验证

### 4.1 开发态运行

```powershell
cd agent-langgraph
.venv\Scripts\python.exe -m uvicorn app.server:app --host 127.0.0.1 --port 8765

cd ..\client
npm run dev
```

### 4.2 离线验证（不调用模型）

```powershell
cd agent-langgraph
.venv\Scripts\python.exe smoke_graph.py    # 图：顺序、并行、两轮返工、闸门
.venv\Scripts\python.exe smoke_server.py   # 服务：异步启动、run_id、轮询、404/409
```

`smoke_server.py` 的断言包含：`/graph/start` < 2s 返回、6 次闸门（含两轮返工后的 generate 闸门）、`rework_count == 2`、未知 run 返回 404、重复 run 返回 409。

### 4.3 构建安装包

```powershell
cd client
npm run prepare-langgraph-sidecar   # 需要 .venv 内安装 pyinstaller
npm run dist:win
```

sidecar 产物位于 `client/vendor/langgraph-sidecar/win32-x64/`，打包后进入 `resources/langgraph-sidecar`；
运行时优先探测，缺失则回退内置编排器，并在页头显示当前模式。

### 4.4 验证结果（本机实测）

| 检查 | 命令 | 结果 |
| --- | --- | --- |
| 类型检查 + 打包 | `cd client; npm run build` | 通过（仅既有 chunk 体积告警） |
| 图拓扑 | `python smoke_graph.py` | `SMOKE OK`，两轮返工、4 个基础闸门 |
| 服务 | `python smoke_server.py` | `/graph/start` 16ms 返回，6 次闸门，`rework_count=2`，404/409 正确 |
| 编排器单测 | `node --test electron/services/pipeline/langgraphOrchestrator.test.cjs` | 4 passed |
| sidecar | `python smoke_sidecar.py` | exe 启动 2.1s，6 次闸门，`rework_count=2`，最终 success |
| 运行自检（GUI 跑完后） | `cd client; npm run inspect:pipeline` | 读取 SQLite，核对 4 闸门 / 打回 / 返工，退出码 0 才可演示 |

> 6 次闸门 = 解析 / 资格 / 法规 / 生成 ×3（两轮返工各重新经过一次生成闸门）。

## 5. 演示脚本

完整分镜、会前清单、失败预案和评委追问见 [演示脚本.md](./演示脚本.md)（8 分钟完整版 + 5 分钟精简版）。

核心原则：**先讲已完成的一轮（成果、指标、知识库、Word、inspect 证据），再现场启动新流水线只演前 1–2 分钟**。整条流水线真实跑一轮约 13 分钟，不适合现场等待；启动新流水线会清空黑板阶段数据，顺序不能反。

三个高光时刻：人工打回重跑、返工评分轨迹（如 62 → 88）、`npm run inspect:pipeline` 四项检查全绿。
